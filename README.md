# ДаДом

Сайт строительной компании: Next.js App Router, React, TypeScript (strict), Tailwind CSS. Существующая дизайн-система сохранена. CMS, CRM, аналитика и отправка заявок не подключены. Каталог и портфолио намеренно пусты до получения реальных материалов.

## Запуск и проверки

Проверено с Node.js 24.22.1 и pnpm 11.25.0. Используйте Node.js 24 LTS и версию pnpm из packageManager.

```sh
pnpm install --frozen-lockfile
pnpm dev
pnpm check:content
pnpm typecheck
pnpm lint
pnpm test
pnpm build
pnpm start
```

Не запускайте dev и production build одновременно в одном каталоге .next. Для независимой проверки в PowerShell:

```powershell
$env:DADOM_BUILD_DIR = ".next-audit"
pnpm build
pnpm start --port 3101
```

В другом терминале: `node scripts/check-http.mjs http://localhost:3101`. Скрипт проверяет HTTP-коды, H1, ресурсы главной и оптимизатор изображений. URL audit-missing зарезервированы для отрицательных проверок. Параметр DADOM_BUILD_DIR должен совпадать при build и start. Он не нужен при обычной разработке.

Тесты используют встроенный node:test и установленный TypeScript; дополнительных тестовых зависимостей нет. Синтетические записи находятся только в tests/fixtures.ts, не в каталоге компании. Временный браузерный тестовый маршрут удалён.

## Структура

- `src/types/content.ts` — HouseProject, PortfolioItem, Complectation, ImageAsset.
- `src/data/content.ts` — три независимых массива и селекторы опубликованных записей.
- `src/data/company.ts` — название, регион, телефон, email, адрес, мессенджеры, юридические данные.
- `src/lib/catalog.ts` — цена с комплектацией, валидация, фильтры, сортировка, пагинация.
- `src/lib/seo.ts`, `src/lib/site.ts` — метаданные и разрешение индексации.
- `src/components/` — карточки, галереи, общие шаблоны страниц.
- `public/images/projects/<slug>/` — изображения типового проекта.
- `public/images/portfolio/<slug>/` — только реальные фотографии построенного объекта.

Данные редактируются без изменения React-компонентов. Изменения статических записей требуют новой сборки и публикации. 50–100 проектов поддерживаются серверной фильтрацией и страницами по 12 записей. В браузер не отправляется весь массив для клиентского поиска. Для частых правок редакторами следующим этапом можно заменить селекторы адаптером CMS, сохранив типы и компоненты.

## 1. Добавление типового проекта

1. Подготовьте утверждённое название, описание, характеристики и права на изображения.
2. Выберите постоянные уникальные id и slug. Slug: строчные латинские буквы, цифры, дефисы. ID используется для связей, slug — для URL. Не меняйте опубликованный slug без плана редиректов.
3. Добавьте запись в массив projects в src/data/content.ts. Все поля ниже обязательны; неизвестные значения — null, списки — [].
4. Оставьте published:false до проверки. Черновик не попадает в списки, прямые страницы и sitemap. Не используйте черновики как хранилище секретных данных.
5. После наполнения выполните check:content, typecheck, test и build. Затем установите published:true, повторите проверки и пересоберите сайт.
6. featured:true повышает приоритет записи на главной. Главная автоматически показывает до трёх опубликованных проектов.

Шаблон ниже — заготовка, не предложение компании. Замените id, slug, название и описание реальными данными:

```ts
{
  id: "replace-project-id",
  slug: "replace-project-slug",
  name: "Заменить утверждённым названием",
  description: "",
  area: null,
  dimensions: null,
  floors: null,
  bedrooms: null,
  rooms: null,
  intendedUse: null,
  architecturalStyle: null,
  price: null,
  priceStatus: "on-request",
  priceCurrency: "RUB",
  pricePackageId: null,
  priceUpdatedAt: null,

  excludedWorks: [],

  published: false,
  seoTitle: null,

```

Площадь — число в м², размеры — строка с единицей измерения, этажи/спальни/комнаты — целые числа. 0 спален допустим; неизвестное значение не заменяйте нулём. Дополнительные характеристики добавляются в specifications: например, ключ с названием характеристики и подтверждённое строковое значение.

## 2. Фотографии и планировки

1. Создайте public/images/projects/<реальный-slug>/.
2. Используйте понятные латинские имена: hero.webp, exterior-01.webp, plan-floor-01.png, plan-floor-02.png.
3. Поддерживаются локальные WebP, JPEG/JPG, PNG, AVIF. Укажите путь от public, без слова public: /images/projects/<slug>/hero.webp.
4. Каждое изображение — объект {src, alt}; width и height необязательны. Alt описывает изображение, а не повторяет рекламные ключевые слова.
5. Обложку поместите в heroImage, остальные виды — в gallery. Обложка автоматически включается в галерею без дублирования.
6. Каждую планировку добавьте в floorPlans. Подпишите этаж в alt. Планировки показываются полностью (object-contain), есть ссылка на оригинал.
7. Визуализации помечайте isIllustration:true. Они не должны выглядеть как доказательство построенного объекта.
8. Проверьте читаемость размеров в оригинале. Для фото обычно достаточно ширины 1600–2400 px; для планов ориентируйтесь на читаемость надписей, а не только размер файла.

Отсутствующее изображение: heroImage:null, gallery:[], floorPlans:[]. Ничего подставлять вместо реальных фотографий не требуется. Проверка перед сборкой обнаруживает указанный, но отсутствующий файл. Ошибка загрузки в браузере заменяется текстовой заглушкой.

## 3. Цена и комплектация

1. Добавьте в complectations запись с уникальным id, утверждёнными name, description, includedWorks и excludedWorks.
2. В проекте перечислите доступные комплектации в packageIds.
3. Для известной цены задайте priceStatus:"known", price — положительное число рублей, pricePackageId — id существующей именованной комплектации, priceUpdatedAt — реальную дату актуализации YYYY-MM-DD.
4. Цена выводится только вместе с названием этой комплектации. Состав указанной комплектации также появится на подробной странице.
5. Если цены нет: priceStatus:"on-request", price:null, pricePackageId:null, priceUpdatedAt:null. Пользователь увидит «Цена по запросу».
6. priceStatus:"not-set" также выводит «Цена по запросу». Не используйте ноль как неизвестную цену.
7. includedWorks/excludedWorks самой записи проекта описывают дополнительные проектные условия. Не противоречьте перечню комплектации и не заявляйте «под ключ» без подтверждённого состава.

Сборка останавливается при известной цене без корректной комплектации, повторяющемся slug/id, неверных числах, отсутствующих связях или файлах. Это намеренная защита от публикации ошибочного предложения.

## 4. Реальный построенный объект

1. Получите разрешение на публикацию фото, описания и географии. Не размещайте точный адрес заказчика без отдельного разрешения.
2. Создайте public/images/portfolio/<slug>/; добавьте реальные фото фасадов, интерьера и этапов работ.
3. Добавьте отдельную запись в portfolio. Типовой проект не превращается в построенный объект автоматически.
4. relatedProjectId — именно id проекта, не slug. Если проект ещё черновик, публичная ссылка на него не показывается. Если связь не нужна — null.
5. constructionPhotos предназначен для фото хода строительства, completedWorks — для реально выполненных работ.
6. Проверьте запись, установите published:true, пересоберите и опубликуйте сайт.

## Контакты, заявки и безопасность

Заполните src/data/company.ts проверенными контактами. Телефон — международный формат; email — адрес; мессенджеры/socialLinks — проверенные HTTPS-ссылки. Не размещайте API-ключи или секреты в данных и NEXT_PUBLIC_*.

Кнопка «Получить расчёт» ведёт на /contacts?project=<slug>. Страница разрешает slug только среди опубликованных проектов, показывает название и ID и явно сообщает, что заявка ещё не отправлена. Для портфолио используется ?portfolio=<slug>. Неизвестные и закрытые записи не раскрываются. Персональные данные не собираются и никуда не отправляются. /thank-you не является рабочим маршрутом до появления подтверждённого серверного результата.

Будущий обработчик должен повторно проверять ID на сервере, валидировать ввод, согласие и защиту от спама, хранить секреты только на сервере и показывать успех только после подтверждённого принятия заявки. Текущий hidden ID — контекст, не средство доверенной авторизации.

## SEO и публикация

По умолчанию весь сайт закрыт от индексации. Настройки задаются перед сборкой, локально — в .env.local:

```dotenv
NEXT_PUBLIC_SITE_URL=https://your-real-domain.ru
SITE_INDEXABLE=false
```

Адрес должен быть HTTPS-доменом без пути, логина, параметров и фрагмента. Пример выше замените реальным доменом. Одного домена недостаточно: SITE_INDEXABLE=true включается только после проверки владельцем контактов, контента, юридических документов и способа связи. После изменения нужна пересборка.

Canonical и Open Graph используют только настроенный домен, никогда localhost. Фильтрованные страницы каталога noindex, canonical указывает на /projects. Черновики не создают маршруты. Пустые каталоги и неподготовленные страницы не включены в sitemap. Страницы /about, /technology, /privacy и /consent сейчас сознательно noindex; после наполнения измените их готовность в pageMetadata и добавьте в sitemap. Это отдельная проверка готовности разделов, не изменение компонентов для каждой записи.

BreadcrumbList появляется при настроенном домене. Не добавлены вымышленные рейтинги, отзывы, LocalBusiness-адрес и коммерческие обещания.
